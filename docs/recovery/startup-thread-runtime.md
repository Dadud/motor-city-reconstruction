# Startup thread runtime recovery

The connected package recovers original thread startup `0x6be4f0`, capacity/allocation initialization `0x6be570`, and page-rounded virtual allocation helper `0x6eedb0`. It reuses the already recovered cleanup registry `0x6bf450` and actual original cleanup identity `0x6be3b0`.

Primary static basis: retained REA Ghidra per-function pseudocode under private export target SHA-256 `28c0cdde77ed24bac6aeeea65699c16be0f31e6aa8cb5db38417f0f3d5880164`. Selected native instruction windows were also inspected as a secondary check of import slots and the tail-call cleanup argument; those Capstone windows are not REA Evidence or complete function ownership assertions. Fresh REA instruction confirmation of the cleanup argument is requested from the integrating worker.

Startup sets its initialized flag before invoking capacity setup, substitutes count 100 only for zero, records thread ID, obtains target process / current thread / source process handles in that order, and calls DuplicateHandle with access 0, inherit false, option 2. The duplicate result is ignored exactly as observed; successful output handle mutation belongs to the platform boundary. Cleanup registration is conditional on the flag after these callbacks, not a stale cached copy.

Capacity initialization first attempts lock-pool acquisition when missing, even if an allocation already exists. It returns the existing allocation identity when present. A new successful allocation invokes the memory-clear boundary and sets capacity from rounded bytes divided by 12; its return word is rounded bytes multiplied by 0xaaaaaaab, preserving original modulo arithmetic rather than substituting the capacity. An allocation failure returns zero without changing capacity.

The allocator caches a page size fetched via GetSystemInfo and computes the original signed quotient from the wrapped numerator `(bytes - 1 + page_size)`, then multiplies modulo 32 bits. Page sizes must be positive signed 32-bit values. This deliberately preserves unusual wrapped input behavior; it does not silently replace the original with unsigned ceiling division.

State holds seven original global words from `0xb2bbc4..0xb2bbdc` plus page size `0xb35fd0`, not a reconstructed original object layout. Lock-pool acquisition, GetSystemInfo, VirtualAlloc, memory clearing and Windows thread/handle APIs are explicit platform callbacks. There is no claim that synthetic identities are valid host handles or that critical section, allocation, release or cleanup lifecycle works in Windows yet.

`tools/startup_thread_runtime_cases.py` executes all three complete original bodies and the actual original cleanup registry registration, substituting only the declared service boundaries. The 1,024 cases include 256 four-call connected sequences, existing/missing resources, initialized/registration flags, allocation and lock failure, duplicate failure, rounded sizes, wrapped count edges, full/duplicate/empty registries and boundary mutation of allocation/capacity/registration. Outputs include return bits, updated byte size, all eight state words, all 64 registry slots and ordered callback arguments/state snapshots. MSVC and Zig comparisons pass every case; domain test checks cached early exits and invalid page size rejection.
