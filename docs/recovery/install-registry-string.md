# Registry string query recovery

Original `0x51d7c0` is recovered as `registry_read_string`. Primary retained REA decompilation is in the private install registry query evidence bundle. The recovered body is independently retained in batch `ev_a6e347252cf77991e82353147b50c1267c1ca696e57a3b4fbdebb1be4ae8a40a` and revalidated in batch `ev_b3ad95cad2414c931a32f2d01905112449ae3af6d0332e830a2426a2279d9f98`. The cell is pinned to mcity.exe SHA-256 `28c0cdde77ed24bac6aeeea65699c16be0f31e6aa8cb5db38417f0f3d5880164`. The apparent neighboring `0x51d830` is inside this recovered body and is not promoted into a separate write routine.

The routine requires a nonzero owner handle, name, output pointer and count. If both key and path first characters are nonzero it reads a zero-initialized 256-byte profile buffer with API size 255. Any nonzero API result selects that buffer, even if its first character is zero. It copies exactly count bytes using strncpy semantics and returns true. This differs from the integer query, which additionally tests the first text character.

If the profile result is zero or the key/path first-character gate is absent, it allocates another zero-initialized 256-byte local and queries the live owner handle with input size 255. The type local is uninitialized in the original. The supported callback contract always writes the resulting type; its pre-write value is intentionally neither read nor compared. Success requires status 0, type 1 and any nonzero resulting size. It does not require returned size to equal count or contain an explicit terminator. Failed checks leave the external destination unchanged.

Native bounded copy preserves padding and nontermination: after the first NUL it fills the remaining requested bytes with zeros, while a count no larger than source text length produces no extra terminator. Bytes beyond the requested count are preserved. The original oracle executes the actual original strncpy body, so copy results are not generated by a substituted copy boundary. Profile and registry calls remain explicit returning synthetic boundaries and may mutate the shared owner; fallback rereads the handle after the profile callback.

Admitted count is 0..256 and nonempty destinations must hold count bytes. Counts above 256 or larger than the writable native destination throw; original-equivalence claims exclude source overreads, destination overflow and owner/output aliasing. A zero count or absent guard input returns false before requiring a platform callback. Profile/query buffers are full 256-byte locals; synthetic payload writes are at most 255 bytes, preserving the zero final byte. Original type-local nonwrites and real Windows resource behavior are not claimed.

The 2,048 complete original-instruction cases cross 64 API status/type/size/mutation profiles, eight counts (0,1,2,4,16,254,255,256) and four key/path/input-guard variants. Payloads cover empty text, short text, high-bit bytes, long text, embedded NUL with trailing bytes and exact-prefix truncation. Full 528-byte owner and 320-byte external images, including the unchanged guard tail, are compared with per-boundary local-buffer, size, owner and output snapshots.

Both MSVC and Zig NDEBUG comparisons pass all cases. Native Release-active tests additionally verify profile success with empty text, padding and absent added terminator, wrong type/zero size, accepted nonzero small size, all zero guards, oversized count rejection and mandatory bridge rejection. No registry, account/credential value or profile file is read or written on the host.
