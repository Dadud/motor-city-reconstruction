# Startup controller recovery

The complete controller `0x6bfa10` and policy setter `0x584c80` now have authored native implementations. The controller preserves prerequisite calls, diagnostic source/line updates, runtime cleanup registration, environment-call order, driver-name selection and fallback, loader/graphics status handling, the graphics-ready early return, policy installation, mouse/input ordering and final viewport calls. Diagnostic callbacks are permitted to return in the verified domain; failure reporting does not become an invented exception or unconditional abort. An initially ready graphics state bypasses driver setup; a newly initialized graphics path reloads its ready flag before continuing.

The policy setter stores the opaque flag at queue offset `0x514`, callback identity at original global `0x89bdd8`, then enables policy handling at queue offset `0x510`. Startup installs flag one and identity `0x6bfc60`. This does not implement subsequent activation/message policy handlers.

The separate launcher bridge is now statically recovered: it creates two global atoms from per-byte lowercase-hex encoded launch strings, then starts `mcity.exe` with `-NPW(<atom1>/<atom2>)`. The client decodes them into two globals, gates the launcher-authenticated startup path on successful parsing, then passes both nonempty values into an indirect account-login subsystem call. The launcher method reads a whitespace-trimmed string and a second untrimmed string; its sign-in UI presents Username and Password text edits, although the exact widget-to-field mapping remains open. The indirect login method target and live network result remain unresolved. See [launcher protocol](launcher-protocol.md).

`StartupState` names fifteen discontiguous observation words, not an original class layout. In enum order their original addresses are: diagnostic callback `0x8c4718`, diagnostic file `0xb2bba4`, diagnostic line `0xb2bba8`, graphics-ready `0x8c45f8`, auxiliary-ready `0xb35fc4`, configuration word `0x8c4690`, driver name `0xb31fe0`, driver-loaded `0xb31fec`, external-driver flag `0xb2c138`, width/height/depth `0x8c4618/1c/20`, mode/flags `0x8c4628/2c`, policy callback `0x89bdd8`. Names whose original purpose is incomplete remain opaque. Driver identities resolve only through supplied mapped string views; original pointers never become host pointers.

2028 complete original cases match MSVC and Zig: 2016 controller calls and twelve policy setter calls. They cover ready/unready branches, null/installed diagnostic callbacks, auxiliary setup, null/empty/present/recommended/default driver names, external-driver bypass, zero/nonzero failure statuses, callbacks changing globals and diagnostic targets, late dimension changes, signed integer-to-float viewport conversion and exact helper arguments/order. Original viewport argument captures include ordinary dimensions, signed extremes and rounding boundaries. Independent native checks verify early return, error reporting, input order, policy stores and 640x480 viewport words.

`StartupInputBinding` routes initialization, keyboard layout and kind-10 callback installation through actual recovered implementations. `InputDeviceCleanupBinding` supplies the actual cleanup registry and shutdown. Shared queue, diagnostic references and callback/table aliases persist. Four twelve-operation original traces connect full startup, key-down/release/latch query, cleanup, explicit re-registration and repeated startup; all 48 operations match both compilers. They include returning graphics-error callbacks, device setup failure, handle/table mutations, keyboard API-target changes and full cleanup tables. A synthetic preceding helper supplies the declared incoming temporary word used by device initialization; its real body remains unresolved. Synchronization, device/type APIs, other cleanup callbacks, renderer, mouse initialization and remaining runtime helpers remain explicit boundaries. Fixture writes to the graphics-ready word are not claimed game APIs.

The project-wide retained corpus checkpoint contains 110 implemented cells, 80,260 routine cases and 88 connected traces. Full comparisons verified all 110 cells and 88 traces against the hash-checked original under MSVC and Zig. At that checkpoint CTest passed 193 MSVC and 195 Zig tests; Python passed 1,000 tests with seven skips. The refreshed inventory contains 213 reviewed entries across 29 modules (25,779 entries total; 11,760 required after dispositions). These are project-wide recovery metrics, not startup-only coverage. Direct launch with the offline profile reaches a blocked `WinExec("nps_MCO.exe")` handoff and exits 0; this does not reach graphics/input startup. Remaining launcher-authenticated startup, helper bodies, OS adapters, resources, full linkage and gameplay acceptance are open.
