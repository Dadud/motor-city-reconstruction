# Device acquisition recovery

The poll wrapper `0x6f0a70`, read/retry wrapper `0x6f0aa0`, and outer poll/read/clear wrapper `0x6f0a30` are implemented in the `input_device_read` cell. Their complete original bodies execute against supplied synthetic virtual methods. The platform bridge models the object's opaque identity and mutable vtable identity; no original or host pointer is dereferenced.

Polling calls offset `0x64`. Reading calls offset `0x24` with object, size and destination. Only statuses `0x8007000c` and `0x8007001e` select acquisition at offset `0x1c`. Acquisition success retries the original method once; acquisition failure returns its own status. Each virtual call reloads the object's vtable. The outer routine ignores the polling result, always reads, and clears exactly the requested bytes when the final read/acquisition result is nonzero. The inner read wrapper leaves failed output data intact. The decompiler's void return on the inner wrappers was corrected using actual EAX flow and caller disassembly.

Verification: 2,808 original cases across all three entry points match MSVC and Zig exactly. Inputs cover zero and nonzero sizes through 64 bytes, success, both selected errors, other positive/negative statuses, first/retry/acquisition combinations, independent poll and read failures, a second acquisition, partial output writes and changes to the vtable during each method. Outputs compare final status, vtable identity, complete buffer and ordered method observations including the complete pre-call buffer. Six synthetic stdcall methods preserve actual argument order and callee stack cleanup. Original retry and zero-fill code is unchanged.

Independent native tests check failed second acquisition, table reloads, exact callback order, successful reads after polling failure, one retry only, inner-wrapper preservation of failed data, outer clearing bounds and zero-sized reads. Both compiler tests pass.

The state accessor `0x6f03c0` is now implemented. Kind 6 runs the actual poll/read/retry/clear wrappers on the 256-byte payload and returns the complete 260-byte keyboard image, preserving its four-byte prefix even on acquisition failure. Disabled kinds 2 and 6 return null. Kind 2 retains the original information helper as an explicit bridge and returns its image only on zero status. Invalid kinds record the original source-location identity and line before the diagnostic callback. Callbacks may change enable/device/diagnostic globals without altering the original branch result.

All 360 accessor cases match MSVC and Zig, including disabled/invalid kinds, successful and failed information requests, diagnostic ordering, callback mutations and keyboard acquisition status combinations. Independent native tests check payload clearing versus prefix preservation, the returned image on failure, disabled access, information side effects and diagnostic ordering.

The four queue lifecycle traces now use `InputTranslationDeviceBinding` to execute the actual state accessor and acquisition wrappers on every scan translation. The four acquisition profiles cover success, final read failure, successful reacquisition/retry, and polling failure followed by successful read. Persistent producers, character messages, repeated peek/pop, caps updates and empty reads share queue, translation and device state. Every operation compares complete images and accumulated callback observations. Both compilers match the original traces. Original state-accessor and poll/read bodies are unchanged; only virtual methods, critical-section imports and the unused information/diagnostic branches use bridges.

The retained corpus now contains 90 implemented cells and 47,586 routine cases, plus 44 connected traces. Full checkpoint verification passes: fresh hash-checked original capture against MSVC and retained original observations against Zig cover all 90 cells and 44 connected traces. Native CTest passes 171 MSVC and 173 Zig tests. Python passes 989 tests with seven skips, plus 15 corpus/layout tests repeated after metadata refresh. Inventories record 156 explicitly reviewed main-executable entries. These counts do not measure whole-game completion. Actual device methods, device-information enumeration (`0x6f0b20`), live platform behavior and process cleanup remain unfinished.

## Next enumeration preflight

Initial disassembly of `0x6f0b20` confirms cdecl arguments (device, 540-byte destination). It clears the destination, requests the 580-byte instance record through virtual offset `0x3c`, copies two bounded names, then requests a 44-byte capabilities record through offset `0x0c`. The decompiler's apparent incoming-EBX flag dependency is misleading: `0x6f0bc8` loads capabilities flags from the local record into EAX, and `0x6f0bce` clears EBX before enumeration. Flag conversion uses that EAX value at `0x6f0bd0..0x6f0be9`. Enumeration and all failure branches still require recovery and original comparison; this preflight is not an implemented disposition.
