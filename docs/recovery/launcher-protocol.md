# Launcher to client startup protocol

`mco-launcher.exe` starts `mcity.exe` directly and supplies two Win32 global atoms through its command line. This is the bridge into the client startup code, separate from the `nps_MCO.exe` handoff observed when the client itself is launched directly without launcher atoms.

The launcher `launch::play` body at `0x1401f0d40..0x1401f13f2` accepts the installation path and two byte strings. It hex-encodes each byte string with Rust `LowerHex`, registers each encoded string with `GlobalAddAtomA` through `launch::add_atom`, and builds the client path by appending `mcity.exe` to the supplied installation path. It formats the two returned atom IDs as lowercase hexadecimal in `-NPW(<atom1>/<atom2>)`, then calls `CreateProcessA` with the client executable and that command line. The `add_atom` body at `0x1401f14f0..0x1401f1598` reports an error if atom creation returns zero and otherwise returns the atom ID. Client routine `0x523ed0` parses the same `-NPW(%x/%x)` shape, reads and deletes both atoms, and hex-decodes their payloads into the two startup globals.

This confirms that the launcher supplies the two atom values expected by the client's early parser. It does not establish that the launched client reaches graphics/input startup, authenticates successfully, or behaves like the server-era service. The direct-client offline probe remains a separate branch: its atom parser returned zero, the installation check returned zero, and the client attempted the `nps_MCO.exe` handoff before exiting. That child was blocked by the probe.

Primary static evidence is pinned to launcher SHA-256 `2c1f8f64eb97146d94a6ce3b59bfa0e0d68c048f9f79427e4e1ef20c2372e826` and Ghidra 12.1.4. `launch::play` body and call graph: `ev_2aaf730eafe9d3494d216b032b2d9c36c60b24b782afcfe2278c6db62a88cba0`; `launch::add_atom`: `ev_99ef7610150a00fd27eb2066cdd1c55618f1ecc349108fd82414553cb6322055`; per-byte LowerHex conversion: `ev_df7696598632ca99aae0f905934f0beba5a630e5d672c4e989a23858585dc00f`. The `mcity.exe` literal and atom command format bytes are `ev_f0cd4b2cca5a4b943c1b66ef4496acb611469038ad607ec5c8ab1e7e886ebcd2` and `ev_f05a0949e7bacb8d81f63d01e97fbc268e06e6ef2880bb969ff652b1c0948715`. The client parser is covered by `ev_4966edd3dc44801b7ec819c398dd8b348cea5cf09915a752de9903cab02f579a`. The complete private evidence bundle and compatible snapshot are ignored under `evidence/launcher-protocol-primary.*`.

The decompiler identifies the two launch arguments as byte slices, but this analysis does not trace their UI/storage origins or inspect live values. No account values were captured. Launcher updater, login/network behavior, and end-to-end live startup remain separate recovery work.
