# Launcher to client startup protocol

`mco-launcher.exe` starts `mcity.exe` directly and supplies two Win32 global atoms through its command line. This is the bridge into the client startup code, separate from the `nps_MCO.exe` handoff observed when the client itself is launched directly without launcher atoms.

The launcher `launch::play` body at `0x1401f0d40..0x1401f13f2` accepts the installation path and two byte strings. It hex-encodes each byte string with Rust `LowerHex`, registers each encoded string with `GlobalAddAtomA` through `launch::add_atom`, and builds the client path by appending `mcity.exe` to the supplied installation path. It formats the two returned atom IDs as lowercase hexadecimal in `-NPW(<atom1>/<atom2>)`, then calls `CreateProcessA` with the client executable and that command line. The `add_atom` body at `0x1401f14f0..0x1401f1598` reports an error if atom creation returns zero and otherwise returns the atom ID. Client routine `0x523ed0` parses the same `-NPW(%x/%x)` shape, reads and deletes both atoms, and hex-decodes their payloads into globals `0x00a389e0` and `0x00a38a04`. Its hex conversion helper accepts decimal and upper/lowercase A-F; other characters are logged as invalid and convert to zero.

The client's startup routine calls this parser before its launcher-authenticated initialization path. A failed atom parse selects the separate `nps_MCO.exe` fallback and returns; a successful parse continues through install validation and client startup. Later, the login path checks that both decoded global strings are nonempty, logs `Account_LogOn`, and passes pointers to both strings to an indirect account-subsystem method at vtable offset `+0x0c`, along with additional login parameters and scratch buffers. The method target is unresolved, so the evidence establishes the values reaching the client login subsystem, not the network protocol or a successful server login. Evidence: parser `ev_4966edd3dc44801b7ec819c398dd8b348cea5cf09915a752de9903cab02f579a`; startup gate/fallback `ev_3d4423704ca3bdb5406c0a2ffc2e9285f2a0679fe410223827f77cd741f5ef33`; nonempty check `ev_95e8bcd89c6db3b777ba92317e137c739682566d2da643d8408665e73d21239b`; `Account_LogOn` logging and subsystem call `ev_616b857bdf1dd389ac2df709fecf3a44c7e46e2a5ca10bf4a64e60645d7e1a48`; hex conversion `ev_74fc74785f85a0dc53fd7bdb501e5065a3425355fad00a9bbbf12e78fd64648a`.

The input origin is now narrowed to the launcher's sign-in flow. `LauncherApp::launch` reads the first string from receiver fields at offsets `0x25/0x26`, trims its surrounding whitespace, and passes it as the first byte slice; it passes the second string from offsets `0x28/0x29` unchanged. The sign-in UI builds `Username` and `Password` text edits. This makes the two atom payloads consistent with username and password values, but the static field-to-widget storage mapping is not fully recovered. Evidence: launch method and field reads `ev_bb346b1ee683526720c3489b6c304bd5de75e2034c0632b892862342ac4b1af7`; sign-in widgets and `LOGIN` action `ev_066d8511d419e52c28eb98e311b6c708f70dc9e91754ed3126f0e02f17fb33ea`.

This confirms how the launcher supplies both strings and that the client routes them into its account-login subsystem. It does not establish a successful network login or whether the client reaches graphics/input startup in an environment with the original service. The direct-client offline probe remains a separate branch: its atom parser returned zero, the installation check returned zero, and the client attempted the `nps_MCO.exe` handoff before exiting. That child was blocked by the probe.

No live account values were captured. The launcher's sign-in/network implementation, the target and behavior behind the client's indirect account method, server-era protocol details, and end-to-end live startup remain open.
