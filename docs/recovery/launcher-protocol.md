# Launcher to client startup protocol

## Launcher application recovery

This section recovers the shipped Rust launcher, rather than claiming a replacement launcher implementation. The reconstruction repository contains the native-client reconstruction; the launcher binary is an installation artifact and is separately classified as launcher/updater in `dispositions.json`.

The launcher exposes sign-in, account creation, password reset, settings, patch/update, and self-update flows. Its service calls are built over WinHTTP and use the selected endpoint profile or explicit host/port overrides. The built-in profiles include production (`launcher.novaserv.cc`) and staging (`launcher-stg.novaserv.cc`); the channel selection also includes `local`. The network wrapper sets 12-second resolve/connect/send/receive timeouts, sends the chosen HTTP verb/path, receives the response, and reads the body. These are static observations; no current service availability or server-side behavior is implied. Evidence: endpoint selection `ev_99d34647467187811bf7fda0ba8904f934b11c9dfb6c6a5fdb828d4b835123c1`; WinHTTP transport `ev_e91c6d991a38cd465b702545679192510500cbcc0c12483838e61982adf40cb4`; response wrapper `ev_a663da73516c5f3ed3569bc5c932e08c9b1f3952126dabbf0b1498311e016e14`.

The login request posts to `/launcher/login`. Its JSON contains `username`, `password`, `create`, `remember`, and a device report. The sign-in action passes `create=false`; the account-creation flow uses the same request routine with the create flag enabled. The launcher expects HTTP 200 before deserializing a typed `LoginResponse`. The UI handles success and denial variants, with success able to return a token for remembered sign-in. Evidence: `net::login` `ev_720141fe015a34e90df876804bf9447b14ddd117f01ca5050a0f5f84a33336a3`; sign-in caller `ev_a638a8170ebbbca641e6696b21ab6f7b0130a54ad2f72cbe5b8b6952de3608b8`; sign-in screen `ev_5f1da4844d42acf339ed554a3d734e05461298f8464bd8e8f3e58a5d9ccd1115`.

Password reset posts `username`, `code`, and `new_password` to `/launcher/reset` and parses a typed `ResetResponse` only on HTTP 200. The UI exposes reset-code and new-password inputs. The server's code-delivery mechanism and response semantics cannot be inferred from the client binary. Evidence: reset request/response routine `ev_a95ac836f57e1da347ca366188bcf52fb36e61c3d32547914918256c8d300f` (large retained analysis; inspected through REA's continuation view).

Remembered sign-in stores a token, not the password. The launcher reads registry values under its launcher settings, hex-decodes the saved ciphertext, and calls `CryptUnprotectData` with a fixed description/entropy blob before restoring the token. Successful login can save the returned token by calling `CryptProtectData`, hex-encoding the result, and writing the registry values. The settings action clears these saved values. The UI explicitly describes the token as revocable and encrypted for the Windows account. Evidence: load `ev_179c659888498acaa95e030845c2b025a3cd56da1e635dfb2e1e60c5800396f5`; clear `ev_8e34e3f2720f269057ae71c9f5c3142d0881c141ffc2c4b8ed5c356f3eb70eba`; the token wording is present in the shipped launcher strings.

Patch/update is a separate worker. It fetches and parses a typed manifest, compares manifest/current version values, plans path-based changes, downloads required content, verifies SHA-256 values, and applies/removes files while sending phase/progress messages back to the UI. The manifest has a nine-field type. Its exact schema, server-generated contents, and all failure/retry semantics have not been independently validated against a live service. Evidence: `patch::run` `ev_3853f6b3bdb759fcdbf4f18a997d371e861fbc13faa5782103f4ee8b0953faca`; manifest request/parser `ev_e3294b3144e761f6f478c1aa21702ba461edf299e2bcb209a7b3fc6d006f4e4e`.

The launcher also has a self-update path. Its `suffixed` helper preserves a file's parent and constructs a sibling name by inserting a suffix before a terminal three-byte UTF-8 code point/extension boundary when its byte pattern matches, otherwise appending the supplied suffix. `start_update_check` is a distinct asynchronous worker. The full update acquisition/signature/trust chain and final replacement behavior remain open; a helper and UI string inventory alone do not establish them. Evidence: helper `ev_a3bd2c2ce835dccdb2c2ce83d7b4b6d606bee564fb639e69d88401a4f38074ec`; check startup `ev_fa2f654fc9a88d54b5e940e9976c519027c1617e57d36d313f798aaaae834d31`.

The launcher-to-client handoff is detailed below. Important open items across the whole launcher are the exact sign-in widget-to-state mapping, complete account/reset result-to-UI messages, complete manifest schema and patch semantics, self-update trust and replacement flow, and live end-to-end behavior. Static analysis of the shipped launcher does not show that a live login or a playable session currently succeeds.

`mco-launcher.exe` starts `mcity.exe` directly and supplies two Win32 global atoms through its command line. This is the bridge into the client startup code, separate from the `nps_MCO.exe` handoff observed when the client itself is launched directly without launcher atoms.

The launcher `launch::play` body at `0x1401f0d40..0x1401f13f2` accepts the installation path and two byte strings. It hex-encodes each byte string with Rust `LowerHex`, registers each encoded string with `GlobalAddAtomA` through `launch::add_atom`, and builds the client path by appending `mcity.exe` to the supplied installation path. It formats the two returned atom IDs as lowercase hexadecimal in `-NPW(<atom1>/<atom2>)`, then calls `CreateProcessA` with the client executable and that command line. The `add_atom` body at `0x1401f14f0..0x1401f1598` reports an error if atom creation returns zero and otherwise returns the atom ID. Client routine `0x523ed0` parses the same `-NPW(%x/%x)` shape, reads and deletes both atoms, and hex-decodes their payloads into globals `0x00a389e0` and `0x00a38a04`. Its hex conversion helper accepts decimal and upper/lowercase A-F; other characters are logged as invalid and convert to zero.

The client's startup routine calls this parser before its launcher-authenticated initialization path. A failed atom parse selects the separate `nps_MCO.exe` fallback and returns; a successful parse continues through install validation and client startup. Later, the login path checks that both decoded global strings are nonempty, logs `Account_LogOn`, and passes pointers to both strings to an indirect account-subsystem method at vtable offset `+0x0c`, along with additional login parameters and scratch buffers. The method target is unresolved, so the evidence establishes the values reaching the client login subsystem, not the network protocol or a successful server login. Evidence: parser `ev_4966edd3dc44801b7ec819c398dd8b348cea5cf09915a752de9903cab02f579a`; startup gate/fallback `ev_3d4423704ca3bdb5406c0a2ffc2e9285f2a0679fe410223827f77cd741f5ef33`; nonempty check `ev_95e8bcd89c6db3b777ba92317e137c739682566d2da643d8408665e73d21239b`; `Account_LogOn` logging and subsystem call `ev_616b857bdf1dd389ac2df709fecf3a44c7e46e2a5ca10bf4a64e60645d7e1a48`; hex conversion `ev_74fc74785f85a0dc53fd7bdb501e5065a3425355fad00a9bbbf12e78fd64648a`.

The input origin is now narrowed to the launcher's sign-in flow. `LauncherApp::launch` reads the first string from receiver fields at offsets `0x25/0x26`, trims its surrounding whitespace, and passes it as the first byte slice; it passes the second string from offsets `0x28/0x29` unchanged. The sign-in UI builds `Username` and `Password` text edits. This makes the two atom payloads consistent with username and password values, but the static field-to-widget storage mapping is not fully recovered. Evidence: launch method and field reads `ev_bb346b1ee683526720c3489b6c304bd5de75e2034c0632b892862342ac4b1af7`; sign-in widgets and `LOGIN` action `ev_066d8511d419e52c28eb98e311b6c708f70dc9e91754ed3126f0e02f17fb33ea`.

This confirms how the launcher supplies both strings and that the client routes them into its account-login subsystem. It does not establish a successful network login or whether the client reaches graphics/input startup in an environment with the original service. The direct-client offline probe remains a separate branch: its atom parser returned zero, the installation check returned zero, and the client attempted the `nps_MCO.exe` handoff before exiting. That child was blocked by the probe.

Primary static evidence is pinned to launcher SHA-256 `2c1f8f64eb97146d94a6ce3b59bfa0e0d68c048f9f79427e4e1ef20c2372e826` and Ghidra 12.1.4. `launch::play` body and call graph: `ev_2aaf730eafe9d3494d216b032b2d9c36c60b24b782afcfe2278c6db62a88cba0`; `launch::add_atom`: `ev_99ef7610150a00fd27eb2066cdd1c55618f1ecc349108fd82414553cb6322055`; per-byte LowerHex conversion: `ev_df7696598632ca99aae0f905934f0beba5a630e5d672c4e989a23858585dc00f`. The `mcity.exe` literal and atom command format bytes are `ev_f0cd4b2cca5a4b943c1b66ef4496acb611469038ad607ec5c8ab1e7e886ebcd2` and `ev_f05a0949e7bacb8d81f63d01e97fbc268e06e6ef2880bb969ff652b1c0948715`. The client parser is covered by `ev_4966edd3dc44801b7ec819c398dd8b348cea5cf09915a752de9903cab02f579a`. The complete private evidence bundle and compatible snapshot are ignored under `evidence/launcher-protocol-primary.*`.

No live account values were captured. The launcher's sign-in/network implementation, the target and behavior behind the client's indirect account method, server-era protocol details, and end-to-end live startup remain open.
